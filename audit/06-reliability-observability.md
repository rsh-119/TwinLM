## Implemented monitoring

`app/observability.py:24-62` defines 16 custom metric families: requests, end-to-end latency, provider latency, TTFT, provider errors, tokens, cost, fallback, retry, cache hit/miss, health, active requests, guardrails, schema failures, rate-limit rejection. Endpoint existence is tested. Prometheus scrapes every 15s (`monitoring/prometheus.yml:1-8`); Grafana dashboard and datasource provisioning are files, not verified running in this audit. Exporter's standard Python/process metrics may be platform-dependent; Windows test availability does not prove Linux container metrics.

Logging is JSON with request ID and formatted-line redaction (`observability.py:124-177`); severity levels distinguish warnings/errors, and httpx URL logging is suppressed. Access log includes method/path/status/duration as message text, not separate structured fields. Timestamp lacks timezone offset. No log shipping/retention, OpenTelemetry spans, trace propagation, collector, alert rules, Alertmanager, or incident runbook was found. Request IDs provide correlation but are not distributed traces.

## Monitoring correctness gaps

F02/F04 cause missing DB usage without corresponding writer-loss metrics; dropped counts only increment on queue full, not batch failure. F07 means request error ratio can understate interrupted streams. Auth/validation failures lack LLM UsageRecord metrics. Summaries/repair provider attempts and cost disagree; provider health gauge changes on publish, not continuously with cooldown. TTFT measures the final provider attempt, not all failed-attempt time from client arrival (`model_router.py:424`). Admin model-group percentiles actually use provider-wide latency samples (`admin.py:45-48`). Arbitrary successful model labels can create metric cardinality growth. Bound labels and define metric semantics before setting alerts.

## Minimal proposed operations stack

Keep JSON stdout, existing Prometheus/Grafana, host/container monitoring and PostgreSQL stats. Add writer depth/oldest age/failed and recovered row counters, DB checkout/query latency, event-loop lag, reserved/unknown spend, completed/interrupted stream counts and context truncation counts. Ship logs to existing host/provider storage with an explicit retention and redaction policy. Add only a few actionable alerts: readiness failures; unexpected error/interrupted-stream ratio; p95/TTFT beyond agreed objective; writer loss or excessive queue age; disk/memory pressure; all providers unavailable; missing backup/restore freshness. Each alert needs an owner and runbook. Tracing is optional after these metrics are accurate.

Proposed SLIs: eligible-request success (exclude expected client 4xx; count incomplete streams); time to first meaningful text/tool event; nonstream response latency; stream completion; ledger settlement completeness; stateful durable-write success; recovery/restore time. Choose window/targets only after owner requirements. HTTP 200 alone is not a valid completion SLI. Financial completeness and data-integrity gates should not be hidden inside availability averages.

Recovery procedure to create: contain unsafe admission, preserve DB/ledger, identify request/server execution IDs, reconcile provider usage without exposing prompts, restore/replay pending records, validate consistency and resume under limits. A DLQ is useful only for a new durable job/ledger mechanism; no current broker exists. Circuit breakers already serve a justified provider-outage role; adding more infrastructure before fixing loss and outcomes would increase operational burden.
